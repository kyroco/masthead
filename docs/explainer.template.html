Masthead, a plugin for Claude Code

Give it the issues. Get back merged pull requests.

Masthead runs your GitHub issues for you: each one in its own session, checked before it starts, reviewed by readers who weren't in the room, tested on the exact commit that ships, and merged. You decide the things only you can decide.

Why we built it

We'd had the rules written down for a long time. "Search memory before you change anything" sat in the file Claude reads at the start of every session. Then we took out the small script that was enforcing it, and within two days a whole piece of work shipped with nothing saved. Nobody noticed until later.

A rule in prose is a suggestion. A rule in front of the action is a rule. That's the idea under all of it: write the spec into the issue before the session starts, let the session run on its own, and put the rules that matter where they can't be forgotten.

A day with Masthead

It's Monday. You have a milestone with nine issues in it, the kind of list that used to mean a week of watching over someone's shoulder. You open Claude Code in the repository and type one thing:

/work-on milestone 4

A foreman wakes up. It doesn't build anything yet. It reads. The project's README first, because that's the brief: why this work exists, what shape it has, what rules it follows. Then every issue, with every comment, because your rulings tend to arrive as comments. Then what earlier sessions wrote down in memory. It notes which decision record, architecture notes and mockups the issues point at, but it doesn't read those end to end yet. Every builder reads them in full, and when a builder asks a question, the foreman reads the section the answer sits in and quotes it. A foreman that reads everything up front runs out of room before the first builder starts.

Then it sends a small agent to every issue, all nine at once. Each one reads its issue and rewrites it on GitHub itself, then hands the foreman only the verdict and the open questions. Each asks the same things. Does this issue say what has to be true when it's done, or does it tell the builder how to do its job? Can I read scenarios out of it, "Given this, When that, Then this is true," and does each one rest on something real: a decision that was made, a rule in the README, something you actually said? Is it too big for one pull request? What would a builder have to guess? When all nine are done, one more agent, on a stronger model, reads every rewritten issue against the decision record, the architecture notes, the mockups and the old body. It puts back anything a rewrite dropped and fixes the order, each fix resting on a line it can quote. It tells you, without changing anything, when two issues build the same thing, one contradicts the decision record, or a decision has nobody building it.

The big ones get split into sub-issues by the agent that rewrote them. Every open question gets looked up in the sources first, in order: the issue's own comments, the README, the decision record, the architecture doc, the mockups, the memory. Whatever a source settles is written into the issue with the line quoted, so nobody has to ask twice. Whatever nothing settles comes to you, one question at a time, with a recommendation. You answer in a sentence. It goes on the issue in your words. An issue with a question still open stays out of the run until you've answered it.

Now the foreman hands you one table: the issues in build order, which depend on which, which can run side by side without touching the same files, how much effort each one needs, and how many workers it would run at once. You pick a number. Say three.

Three fresh sessions start, each with its own copy of the repository and a branch tied to its issue. Each worker reads its issue, the README and the decision record cover to cover, looks up what earlier sessions learned, and writes a plan, one line per scenario: what it will change and the test that proves it. Then it sends the plan to a verifier that saw none of its reasoning. The verifier reads only the plan, the issue and the decisions the issue names, and answers five questions: does it over build, does it cut corners, does it add things nobody asked for, does it find the holes in the design and fill them, and does it get to a correct result in the least time. It also says if any step undoes a recorded decision. A plan that fails is revised; one that fails twice stops and asks. When it passes, the worker tells the foreman and builds.

Then they build. A bug is fixed test first: a failing test in its own commit, then the fix. When an issue builds a decision record, a fresh reviewer reads the whole record and checks the work against it, assuming it was done wrong.

When a worker thinks it's done, it doesn't grade its own work. For each scenario it sends one verifier the scenario, the decision lines it rests on, the diff, and two lists: what it claims works and what it could not prove. Nothing else: not its notes, not an earlier review. The verifier assumes the code is wrong and tries to prove it, with every way a change goes wrong as its methods: a write that fails halfway, an input nobody handled, a promise to a caller the code breaks, a shared module written again, a sentence a customer reads that is false in some state. For every claim it returns either "true in every state", with the run that shows it, or each state where it is false, with the run. A security reviewer joins when the change touches sign-in, secrets or input from outside, with the repository's security rules as its claims. None of them can edit anything. None of them can reach the network. Then a judge reads the code and the false claims, runs each reproduction it can, confirms it, and places each one: fixed in this pull request, or filed as a new issue. That placement is final. The worker fixes the list, test first again, and only the claims the fix broke go back to a verifier, at most twice. The tests run on the final commit and leave a receipt that names it, and nothing can be pushed until the receipt matches. Then one pull request goes up, with Fixes #41, the list of what wasn't proved, the count of agent runs it took, and the issue moves to In Review.

Meanwhile you're having coffee. A worker's question lands at the foreman, which re-reads the issue's comments and the sources and answers with the line quoted. Only when nothing settles it does the question reach you, and your answer goes on the issue so the next session finds it. A worker that stops on a failure gets one message; a second failure parks the issue with a comment saying what happened, and the run goes on without it.

When a pull request's checks pass, its review is clean and the worker has cleaned up after itself, the foreman queues it to be merged. It closes the issue, and any big issue whose pieces are now all done, then gives that worker its next issue, a follow-up that waited on this one first. By the end of the day every issue is merged, parked or skipped, and you get one line per issue saying which.

The whole time, a set of small checks runs underneath. Nobody, not a worker, not a verifier, not Claude in a hurry, reads a secret, force-pushes, pushes untested code, or sends a verifier a brief with no claims to check. You don't see those checks unless one says no, and when it does, it says why and what to do instead.

One issue on its own

/work-on #123 does the same for a single issue with you as the foreman. The worker reports its brief and waits for your go before building, and an issue with the design-sheet label gets a one-page sheet written into the issue for you to approve first.

Installing it

Open Claude Code in a repository and run these two inside the session, not in a terminal, because only the in-session install asks you the four install options (a terminal install takes the defaults silently):

/plugin marketplace add kyroco/masthead
/plugin install masthead@masthead

It asks whether to connect Korium memory (off unless you say so), whether to keep AI attribution out of commits (on), and whether a helper needs a reason before running on the biggest model (off). Then run /masthead:setup. It asks three questions about the repository and writes nothing until you say yes: just you or the team (whether the settings are committed with the code), tests before a push (it finds your test command), and whether to connect a memory now, later or not at all. Run it again whenever you want to change an answer.

To change an install option later, run /plugin configure masthead@masthead:

What an issue has to say

An issue says what is true when the work is done, never how to get there, in four parts: Why (what a person can't do today), Scenarios (at least one line of "Given, When, Then", each naming the decision, README rule or your own words it rests on), Out of scope, and Questions (what the sources don't settle). One issue is one pull request, built and proved by one worker in one session. The issue checks rewrite issues into this shape and split the ones that are too big, so you don't have to write them this way yourself.

Every check, what it refuses, and where it falls short

Each check is a short script, run by Claude Code at a fixed moment: before a tool call, after one, or when a session or helper stops. It reads what is about to happen and either lets it through or refuses it with a reason Claude can act on. The off switches are environment variables read from the check's own environment, so a session can't switch a check off for itself.

Where these three fall short, together: the fact names a file, and the copy that runs is the one in the checkout you are in. A branch can change the push check script or the toolchain file, the same way CI runs a pull request's own tests. The record of which commit passed is a file in the checkout too. So the push check is a guard against forgetting, not against intent; a pull request review is the guard against intent.

What Masthead never does

  • Send anything anywhere. There's no telemetry. The only network use is the Korium memory, and only if you connect it.
  • Change your code on its own. The checks refuse actions; they don't take them.
  • Read a secret file, not even to check it.
  • Touch your git history. No co-author trailers, no footers.
