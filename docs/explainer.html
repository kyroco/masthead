Masthead, a plugin for Claude Code

Give it the issues. Get back merged pull requests.

Masthead runs your GitHub issues for you: each one in its own session, checked before it starts, reviewed by readers who weren't in the room, tested on the exact commit that ships, and merged. You decide the things only you can decide.

Why we built it

We'd had the rules written down for a long time. "Search memory before you change anything" sat in the file Claude reads at the start of every session. Then we took out the small script that was enforcing it, and within two days a whole piece of work shipped with nothing saved. Nobody noticed until later.

A rule in prose is a suggestion. A rule in front of the action is a rule. That's the idea under all of it: write the spec into the issue before the session starts, let the session run on its own, and put the rules that matter where they can't be forgotten.

A day with Masthead

It's Monday. You have a milestone with nine issues in it, the kind of list that used to mean a week of watching over someone's shoulder. You open Claude Code in the repository and type one thing:

/work-on milestone 4

A foreman wakes up. It doesn't build anything yet. It reads. What earlier sessions wrote down in memory first. Then the project's README, because that's the brief: why this work exists, what shape it has, what rules it follows. Then every issue, with every comment, because your rulings tend to arrive as comments. It notes which decision record, architecture notes and mockups the issues point at, but it doesn't read those end to end yet. Every builder reads them in full, and when a builder asks a question, the foreman reads the section the answer sits in and quotes it. A foreman that reads everything up front runs out of room before the first builder starts.

Then it sends a small agent to every issue, all nine at once. Each one reads its issue and checks it against its sources, on a fixed list. Are the four parts there, in order? Is every line you wrote still quoted under the scenario it rules on? Does each scenario cite a source line that exists, one the agent opens and quotes: a decision that was made, a rule in the README, something you actually said? Can a test show it, "Given this, When that, Then this is true"? Does it say what has to be true when it's done, or does it tell the builder how to do its job? Does it fit one worker session? An issue that passes is left alone: no edit, no comment. One that fails gets only the failing part fixed, on GitHub, and a check in front of the edit refuses a body that drops a line quoted as yours (three or more words in quotes, with your name on the line or on a heading above it), or that adds a question for you without saying where it looked first. Each agent hands the foreman only its verdicts and the open questions. When all nine are done, one more agent, on a stronger model, reads every issue against the decision record, the architecture notes, the mockups and the old body. It puts back anything an edit dropped and fixes the order, each fix resting on a line it can quote. It tells you, without changing anything, when two issues build the same thing, one contradicts the decision record, a decision has nobody building it, or an issue is still too big for one session.

The big ones get split into sub-issues by the agent that checked them. Every open question gets looked up in the sources first, in order: the issue's own comments, the README, the decision record, the architecture doc, the mockups, the memory. Whatever a source settles is written into the issue with the line quoted, so nobody has to ask twice. Whatever nothing settles comes to you, one question at a time, with a recommendation. You answer in a sentence. It goes on the issue in your words. An issue with a question still open stays out of the run until you've answered it.

Now the foreman tells you, in one sentence, what it is about to do, and asks how many workers. You pick a number. Say three. It names the three issues that fill those slots, each with what the customer gets, and brings you the questions those issues still carry, one at a time, in plain words. You answer; each answer goes onto the issue in your words. Then it tells you how far the queue of issues with no open question runs behind them, and takes the next questions whenever you want, so the run never waits on one. The order, the effort each worker runs at and what can run side by side are its calls, and it does not hand you a table to judge them by.

Three fresh sessions start, each with its own copy of the repository and a branch tied to its issue. Each worker reads its issue, the README and the decision record cover to cover, looks up what earlier sessions learned, and builds. It writes no plan and waits for no go: the design was reviewed before the issues were written, and the verifier checks each scenario once the code exists. A worker is done when every scenario has a test that passes, the screens the issue touches work, the push check passes and the pull request is open. Then it stops.

Then they build. A bug is fixed test first: a failing test in its own commit, then the fix. Anything a worker notices that the issue didn't ask for is an extra. It scores each one from 1 to 10, where 10 means leaving it would cause a catastrophic failure, and brings you only what scores 8 or higher. The rest is dropped, not filed.

When a worker thinks it's done, it doesn't grade its own work. For each scenario it sends one verifier the scenario, the decision lines it rests on, the README's opening paragraph on who uses the product, the abilities line and the mockup page the scenario rests on, the diff, and two lists: what it claims works and what it could not prove. Nothing else: not its notes, not an earlier review. The verifier assumes the code is wrong and tries to prove it, with every way a change goes wrong as its methods: a write that fails halfway, an input nobody handled, a promise to a caller the code breaks, a shared module written again, a sentence a customer reads that is false in some state. It tries only states production can reach, starting from a real entry point such as a route, a job or a webhook. For every claim it returns either "true in every state", with the run that shows it, or each state where it is false, with the run; never partly. A security reviewer joins when the change touches sign-in, secrets or input from outside, with the repository's security rules as its claims. None of them can edit anything. None of them can reach the network. Then a judge, given the same product context and nothing from the worker, reads the code along each verifier's path without running the tests a third time, and places each finding that holds: fixed in this pull request when a scenario's Then is false, something that worked before broke, or words a person reads are now wrong; otherwise an extra, which the worker scores like its own. That placement is final for the worker and the foreman; nobody files anything. The worker fixes the list, test first again, and only the claims the fix broke go back to a verifier, at most twice. The tests run on the final commit and leave a receipt that names it, and nothing can be pushed until the receipt matches. Then one pull request goes up, with Fixes #41, the list of what wasn't proved, the number of agent dispatches it took, and the issue moves to In Review.

Meanwhile you're having coffee. A worker's question lands at the foreman, which re-reads the issue's comments and Korium for an answer you already gave and relays it with the line quoted. Anything you have not answered reaches you one question at a time, in customer words, and your answer goes back verbatim and onto the issue so the next session finds it. The foreman decides how the work runs; what the product does, says or charges, and who may do what, are yours. A worker that stops on a failure gets one message; a second failure parks the issue with a comment saying what happened, and the run goes on without it.

When a pull request is ready, the extras its worker brought come to you one item at a time, and you answer each one: fix now, fix later, or proceed. Fix later is the only way an issue gets filed. When its checks pass, its review is clean, every line is answered and the worker has cleaned up after itself, the foreman queues it to be merged. It closes the issue, and any big issue whose pieces are now all done, then starts the next issue, a fix-later issue that waited on this one first, in that worker in the desktop app or in a fresh session in the terminal. By the end of the day every issue is merged, parked or skipped, and you get one line per issue saying which, with how many merged and how many were filed.

The whole time, a set of small checks runs underneath. Nobody, not a worker, not a verifier, not Claude in a hurry, reads a secret, force-pushes, pushes untested code, or sends a verifier a brief with no claims to check. You don't see those checks unless one says no, and when it does, it says why and what to do instead.

One issue on its own

/work-on #123 does the same for a single issue with you as the foreman. The worker tells you in a few lines what it will build and waits for your go.

Installing it

Open Claude Code in a repository and run these two inside the session, not in a terminal, because only the in-session install asks you the four install options (a terminal install takes the defaults silently):

/plugin marketplace add kyroco/masthead
/plugin install masthead@masthead

It asks whether to connect Korium memory (off unless you say so), whether to keep a code index in Korium (off), whether to keep AI attribution out of commits (on), and whether a helper needs a reason before running on the biggest model (off). Then run /masthead:setup. It asks three questions about the repository, or two when a memory is already connected, and one or two more when it finds a folder of decision records or no ignore line for its working files, and writes nothing until you say yes: just you or the team (whether the settings are committed with the code), tests before a push (it finds your test command), and whether to connect a memory now, later or not at all. Run it again whenever you want to change an answer.

To change an install option later, run /plugin configure masthead@masthead:

What an issue has to say

An issue says what is true when the work is done, never how to get there, in four parts: Why (what a person can't do today), Scenarios (at least one line of "Given, When, Then", each naming the decision, README rule or your own words it rests on), Out of scope, and Questions (what the sources don't settle). One issue is one pull request, built and proved by one worker in one session. The issue checks hold each issue to this shape and its sources, fix only the part that fails, and split the ones that are too big, so you don't have to write them this way yourself.

Every check, what it refuses, and where it falls short

Each check is a short script, run by Claude Code at a fixed moment: before a tool call, after one, or when a session or helper stops. It reads what is about to happen and either lets it through or refuses it with a reason Claude can act on. The off switches are environment variables read from the check's own environment, so a session can't switch a check off for itself.

What Masthead never does

  • Send anything anywhere. There's no telemetry. The only network use is the Korium memory, and only if you connect it.
  • Change your code on its own. The checks refuse actions; they don't take them.
  • Read a secret file, not even to check it.
  • Touch your git history. No co-author trailers, no footers.
