Masthead, a plugin for Claude Code

Give it the issues. Get back merged pull requests.

Masthead runs your GitHub issues for you: each one in its own session, checked before it starts, reviewed by readers who weren't in the room, tested on the exact commit that ships, and merged. You decide the things only you can decide.

Why we built it

We'd had the rules written down for a long time. "Search memory before you change anything" sat in the file Claude reads at the start of every session. Then we took out the small script that was enforcing it, and within two days a whole piece of work shipped with nothing saved. Nobody noticed until later.

A rule in prose is a suggestion. A rule in front of the action is a rule. That's the idea under all of it: write the spec into the issue before the session starts, let the session run on its own, and put the rules that matter where they can't be forgotten.

A day with Masthead

It's Monday. You have a milestone with nine issues in it, the kind of list that used to mean a week of watching over someone's shoulder. You open Claude Code in the repository and type one thing:

/work-on milestone 4

A foreman wakes up. It doesn't build anything yet. It reads. The project's README first, because that's the brief: why this work exists, what shape it has, what rules it follows. Then every issue, with every comment, because your rulings tend to arrive as comments. Then the decision records the issues point at, the architecture notes, the mockups, and what earlier sessions wrote down in memory.

Then it sends a small reader to every issue, all nine at once. Each reader comes back with the same report. Does this issue say what has to be true when it's done, or does it tell the builder how to do its job? Can I read scenarios out of it, "Given this, When that, Then this is true," and does each one rest on something real: a decision that was made, a rule in the README, something you actually said? Is it too big for one pull request? What would a builder have to guess? One more reader looks at the milestone as a whole: are two issues building the same thing, does one contradict the decision record, is there a decision nobody is building, is the order right.

The foreman shows you the first issue rewritten, old body beside new, and you say go. The rest get rewritten the same way. The big ones get split into sub-issues. Every open question gets looked up in the sources, in order: the issue's own comments, the README, the decision record, the architecture doc, the mockups, the memory. Whatever a source settles is answered on the issue with the line quoted, so nobody has to ask twice. Whatever nothing settles comes to you, one question at a time, with a recommendation. You answer in a sentence. It goes on the issue in your words. An issue with a question still open stays out of the run until you've answered it.

Now the foreman hands you one table: the issues in build order, which depend on which, which can run side by side without touching the same files, how much effort each one needs, and how many workers it would run at once. You pick a number. Say three.

Three fresh sessions start, each with its own copy of the repository and a branch tied to its issue. Each worker reads its issue, the README and the decision record cover to cover, looks up what earlier sessions learned, and sends the foreman a plan in five lines or fewer: for each scenario, what it will change and the test that proves it. The foreman holds that plan against the scenarios and the README's rule that the simplest thing that meets the result wins, and says go, or sends it back naming the line.

Then they build. A bug is fixed test first: a failing test in its own commit, then the fix. When an issue builds a decision record, a fresh reviewer reads the whole record and checks the work against it, assuming it was done wrong.

When a worker thinks it's done, it doesn't grade its own work. It sends the diff, and nothing else, to five reviewers at once, one angle each: bugs, edge cases, contracts, reuse, cleanup, and a security reviewer when the change touches sign-in, secrets or input from outside. None of them saw the worker's notes. None of them can edit anything. None of them can reach the network. Then a judge reads the code and their findings, throws out whatever it can't prove, and hands back a fix list with a file and a line for each item. The worker fixes those, test first again, and the fixes get a check of their own. A reader goes over any sentence a customer would read and says which is false against the scenarios and which isn't plain English. The tests run on the final commit and leave a receipt that names it, and nothing can be pushed until the receipt matches. Then one pull request goes up, with Fixes #41, the list of what wasn't proved, and the issue moves to In Review.

Meanwhile you're having coffee. A worker's question lands at the foreman, which re-reads the issue's comments and the sources and answers with the line quoted. Only when nothing settles it does the question reach you, and your answer goes on the issue so the next session finds it. A worker that stops on a failure gets one message; a second failure parks the issue with a comment saying what happened, and the run goes on without it.

When a pull request's checks are green, its review is clean and the worker has cleaned up after itself, the foreman queues it for merge, closes the sub-issues that shipped, and gives that worker the next ready issue. By the end of the day every issue is merged, parked or skipped, and you get one line per issue saying which.

The whole time, a set of small checks runs underneath. Nobody, not a worker, not a reviewer, not Claude in a hurry, reads a secret, force-pushes, pushes untested code, or sends a helper a brief that hides what wasn't proved. You don't see those checks unless one says no, and when it does, it says why and what to do instead.

One issue on its own

/work-on #123 does the same for a single issue with you as the foreman. The worker reports its brief and waits for your go before building, and an issue with the design-sheet label gets a one-page sheet written into the issue for you to approve first.

Installing it

claude plugin marketplace add kyroco/masthead
claude plugin install masthead@masthead

Then open Claude Code in a repository and run /masthead:setup. It asks three questions and writes nothing until you say yes: just you or the team (whether the settings are committed with the code), tests before a push (it finds your test command), and whether to connect a memory now, later or not at all. Run it again whenever you want to change an answer.

The install options are under /plugin configure masthead@masthead:

To remove it: claude plugin uninstall masthead@masthead. The settings file setup wrote and the push check script are yours to delete.

What an issue has to say

An issue says what is true when the work is done, never how to get there, in four parts: Why (what a person can't do today), Scenarios (one to five lines of "Given, When, Then", each naming the decision, README rule or your own words it rests on), Out of scope, and Questions (what the sources don't settle). One issue is one pull request, built and proved by one worker in one session. The issue checks rewrite issues into this shape and split the ones that are too big, so you don't have to write them this way yourself.

Every check, what it refuses, and where it falls short

Each check is a short script, run by Claude Code at a fixed moment: before a tool call, after one, or when a session or helper stops. It reads what is about to happen and either lets it through or refuses it with a reason Claude can act on. The off switches are environment variables read from the check's own environment, so a session can't switch a check off for itself.

What Masthead never does

  • Send anything anywhere. There's no telemetry. The only network use is the Korium memory, and only if you connect it.
  • Change your code on its own. The checks refuse actions; they don't take them.
  • Read a secret file, not even to check it.
  • Touch your git history. No co-author trailers, no footers.
